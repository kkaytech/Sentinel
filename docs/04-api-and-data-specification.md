## 2. API Conventions

### 2.1 General

- **Base path and format.** The base path is `/api/v1`. Requests and responses are JSON (`application/json; charset=utf-8`), except for uploads (multipart) and downloads.
- **Naming.** Field names use `snake_case`. IDs are UUID strings. Money is a string with 2 decimal places, always paired with `currency`.
- **Pagination.** List endpoints take `limit` (default 50, maximum 200) and `offset`. Responses have the shape `{ "items": [...], "total": n, "limit": l, "offset": o }`. Ordering is stable and documented for each endpoint.
- **OpenAPI.** The specification is generated by FastAPI. Every operation declares `x-permission` and `x-error-codes` (FR-016.2).

### 2.2 Authentication and CSRF

- **Login.** `POST /auth/login` sets the cookie `sentinel_session` (`HttpOnly`, `SameSite=Lax`, and `Secure` when `SENTINEL_HTTPS=true`) and returns a `csrf_token`.
- **CSRF.** Every `POST`, `PATCH` and `DELETE` must send the header `X-CSRF-Token`. A missing or wrong token returns `403 CSRF_INVALID`.
- **Sessions.** A session expires after 8 hours idle and then returns `401 SESSION_EXPIRED`.

### 2.3 Error envelope

```json
{
  "error": {
    "code": "PUBLICATION_INELIGIBLE",
    "message": "Publication refused: 2 checks failed.",
    "details": { "checks": [ ... ] },
    "correlation_id": "c0a8012e-…"
  }
}
```

The codes are listed in FS §8. `message` is safe to display and never contains a stack trace, SQL or a data cell value.

## 4. Data Model

**Conventions:**
- **Primary keys.** `id uuid PRIMARY KEY DEFAULT gen_random_uuid()` unless noted.
- **Timestamps.** `timestamptz NOT NULL DEFAULT now()`.
- **Status fields.** `text` with a `CHECK` listing the allowed values.
- **Binding tuple.** "Tuple" means four `NOT NULL` columns: `dataset_version_id uuid REFERENCES app.dataset_versions`, `content_hash char(64)`, `validation_run_id uuid REFERENCES app.validation_runs`, `rule_set_version_id uuid REFERENCES app.config_versions`.
- **Grants.** Per ARD §7.3.2. In the tables below, `U(cols)` names the columns `sentinel_app` may `UPDATE`, and `—` means insert-only.

### 4.1 Migration 0001: baseline

The roles themselves are created by the `db` init script (ARD §7.3.1). Migration 0001 then:
- creates the schemas `app`, `data`, `published` and `audit`, owned by `sentinel_owner`;
- applies the baseline revocations;
- grants `USAGE` on the schemas;
- installs the trigger functions `sentinel_forbid_change()` (owner-only `UPDATE`/`DELETE`/`TRUNCATE`) and `sentinel_seal_guard()` (§4.10).

**Currency columns are `text`, not `char(3)`** (decided after PoC-1). Impact is grouped by the raw currency cell, so an invalid code of any length must be storable. Invalid codes are reported as validation findings (`INV_CODE_CURRENCY`) and never as insert failures. A null currency is stored as the empty string.

Estimated reporting impact (FS §5.4) is stored in `kpi_values`, not in `impact_figures`. No column anywhere is named with the word "loss" (BR-007.2).

| `app.jobs` | `id`, `kind CHECK IN (VALIDATION_RUN, AI_EXPLANATION)`, `payload jsonb`, `status CHECK IN (QUEUED, RUNNING, SUCCEEDED, FAILED)`, `created_at`, `claimed_at NULL`, `finished_at NULL`, `error text NULL` | Index `(status, created_at)` | `status, claimed_at, finished_at, error` |

**Why some published columns are nullable.** They are nullable only where a waivable `BLOCKING` rule could let a null be published: `supplier_id`, and the `*_NN_OTHER` columns. `gross_amount`, `currency`, the primary keys and every typed column's parseability are guaranteed by the non-waivable rules.

### 4.10 Guards (clarifies ARD §7.3)

| Guard | Applies to | Rule |
|---|---|---|
| `sentinel_forbid_change` | Every table marked "—" or with column-limited updates | `UPDATE`, `DELETE` and `TRUNCATE` are rejected unless `current_user = 'sentinel_owner'`. Column-limited tables use a per-table trigger variant that allows only the granted columns to change. The privileges already enforce this; the trigger is a second layer. |
| **Seal-on-commit** (`sentinel_seal_guard`) | `data.raw_files`, `data.version_rows`, `app.column_profiles` (parent: version); `published.*` (parent: publication) | Insert allowed only if `parent.creating_xact = pg_current_xact_id()` |
| **Open-parent guard** | `app.findings`, `app.finding_records`, `app.impact_figures`, `app.run_impact_totals`, `app.kpi_values` (parent: run) | Insert allowed only while the parent run's status is `RUNNING`. The run's only transitions are `RUNNING → COMPLETED` or `RUNNING → ERROR`, and the completion transaction writes every child. Once it commits, the run is sealed. |

**ARD clarification.** ARD §7.3.2 lists run children under "seal guard (run)". A run is committed as `RUNNING` first, so its children cannot share its creating transaction. The open-parent guard is the intended mechanism. It is equivalent in effect: nothing can be added after completion. This changes no product behaviour or PRD requirement.

### 7.3 Export package `<publication_ref>.zip`

- **Contents, in fixed order:** `manifest.json`, then `invoices.csv`, then `suppliers.csv`, then `README.txt`. `README.txt` holds verification instructions and the spreadsheet formula warning (R-09).
- **Reproducibility.** Every entry is stored uncompressed (`ZIP_STORED`) with the timestamp 1980-01-01 00:00:00, so the ZIP bytes are deterministic.
- **Verifier.** `python scripts/verify_publication.py <zip> [--expected-manifest-sha256 <hex>]` uses only the Python standard library. Exit codes: 0 `VERIFIED`, 1 `FAILED`, 2 usage error.
